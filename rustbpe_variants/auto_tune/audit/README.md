**Anti-churn (added 2026-06-10/11 after a live limit cycle):** rounds 51–109 cycled a ~6-pair cluster (`ol+ition`, `i+king`, `i+ological`, `or+ning`, `oci+ety`, `ut+ory`) through add → mass LOO-eject → re-add with bit-identical deltas: the members contest the same marginal vocab slots at the 32K tail (lineage shows ` cellul` toggling born/died across the cluster members and their pool neighbors), each is individually best vs the post-eject reference, and greedy commit + LOO retention has no termination guarantee. Two driver mechanisms fixed it. (1) **Eject-cooldown** (`--cooldown-base 4`): a pair's k-th jail event (ejection or veto) benches it from the pool for 4·2^(k−1) rounds — exponential backoff, derived purely from the rounds journal so `--resume`/`--rerun` replay it exactly; on a 0-keep round the earliest-expiring pair is released early, so fixpoint still requires an empty bench. (2) **Transactional net-commit** (`--net-commit`): trial the best keep, settle the LOO ejections it triggers (cascades included), then gate the NET settled-state delta vs the pre-commit reference — net passes → commit + ejections land as one transaction (flipped pairs benched); net fails → revert entirely, veto + jail the candidate, trial the next-best (`--net-retries 6`/round). Rationale: per-pair deltas can't assign blame for an interaction (the trial's own passing delta and the incumbents' LOO failures describe the same conflict), so the net transaction is what's gated; accepted transactions never regress net coverage → monotone progress restored. Observed since net-commit went live (r112): zero standalone cleanup rounds through convergence — the kept set grew 83→129 (r147→r194) on genuinely-new pairs (vs only 6 new across the 38 churn rounds r72–109), then sat flat r194→r300 (106 rounds, 79 vetoes total) with the gate refusing net-negative transactions instead of re-cycling — a stable plateau, not the old limit cycle. Vetoes caught the destructive commits (`ick+er` would have cost net +13.9 comp by flipping `ab+or`+`k+al`); the one accepted transactional ejection was a clean upgrade (16 bench-rounds after its veto, `ick+er` re-auditioned and was ACCEPTED as an `ick+ness`→`ick+er` swap, net Δcov+1/Δcomp−0.9); and the cycle cluster resolved on merit (`i+ological` re-committed cleanly off the bench at r140; the rest competed in the pool without winning).

**Why corpus caching, not parallel subprocesses (resolved):** the earlier `--jobs`/`--train-rayon-threads` parallel runner never paid off live. Measured root cause: a single BPE train already saturates all cores (rayon), so concurrent trains add ~no throughput — and ~85% of a train's wall-time was re-reading/re-tokenizing the *identical* corpus (~143s of ~174s), not the merge loop (~22s). Fix: the `rustbpe_auto_tune` crate's `load_corpus`/`train_from_cached` — read the corpus once, reuse it for every candidate → ~30s/candidate, serial, ~6× faster (`train_from_cached` bit-identical to a full `train_from_iterator`, validated). The old `--jobs 12 ≈ 3.4×` figure was train-only and didn't survive the live measure phase + core contention.

Tooling: `tools.heldout_fixpoint_cached` (driver; adaptive `--mine` candidate pool), `tools.token_lineage` (post-hoc lineage/influence), `tools.audit_trajectory` (metric trajectory + graph), `tools.analyze_logs` (classify LOG rejections by failure mode A/B/C + the class-B near-miss exchange-rate set), `tools.generalization_check_cached` (fixpoint-era fresh-shard check + `--trajectory N` journal-replay frontier; same Rust measurement stack as the gate; the non-cached `generalization_check` predecessor was removed in the 2026-06 cleanup).

## Directions for exploration (after the current audit)

1. **Do single-pair DROPs become valuable in combination?** A block that's inert against the current reference (Δ=0, or whose merge never even forms) is **not proven useless** — it can turn live when (a) a sibling route is also blocked (co-requisite), (b) another block reshapes the merge tree (cascade-enabling), or (c) blocking elsewhere makes this pair's merge `argmax`. We've only tested within-surface-form route-sets on two families (0 keeps); cascade chains, and re-testing DROPs against the final grown reference (order-dependence), are untested. The space is bounded by structure — shared surface forms + morphological cascade chains, not 2^N — so enumerate those families and test them as candidate sets. The cached fixpoint makes this cheap (~30s/set, serial): seed it with the proven reference and feed the combination sets as the candidate list. What's left is enumerating the sets. (A static inert pre-filter does **not** work — see direction (2): static re-encode doesn't predict the retrain verdict, so DROPs can't be cheaply pre-screened; combinations must be tested by retraining.) *Cross-cut (pristine baseline): ~97% of candidate concatenations are real tokens, so single-pair inertness is mostly harmless rerouting, not non-formation — any combination value would come from the rerouting/cascade cases.*

2. **Warm-start the merge loop — DEPRIORITIZED (corpus caching already captured the big win).** The original idea: skip the merges *before* a blocked pair's rank *k* (provably identical until *k*) and recompute only the `(32K − k)` tail. But the measured cost breakdown reframed it: a train is ~143s corpus read + ~22s merge loop, and **corpus caching already eliminates the 143s** (read+tokenize once, reuse for every candidate). Warm-start would only trim the residual ~22s merge loop (and only its prefix) — a small remaining win, not worth the rustbpe snapshot/resume Rust work for now. *(Settled negative result, still useful: a **static re-encode** — drop the merge from the final list, no retrain — does NOT predict the retrain verdict; it omits the slot reallocation + downstream re-derivation that decide it. Validated on round-1's 68 candidates: ≥0 so blind to keeps; spurious cost on retrain-inert DROPs reallocation recovers (`er+ed` gross 303 → net 0); not a reliable bound (`at+ically` gross 19 → +32); and `static=0` ≠ DROP (`ustain+ability` gross 0 → KEEP). So combinations must be tested by retraining — which the cached trainer now makes cheap anyway.)*

3. **Escape the greedy local optimum — NOT built; revisit only if the downstream A/B holds.** The fixpoint is greedy over a non-monotonic gate, so it lands in a *path-dependent local* optimum (commit order is what produced the harmful keeps the net-commit/cleanup now recycle). Two moves search a larger neighborhood for a better final set; both are deferred for the same reason — they optimize the *proxy* (held-out tokenizer metrics) harder, and the audit's effect is marginal, so **don't invest until a speedrun A/B shows the tokenizer changes move model training** (the 2026-06-14 d24 A/B is a *borderline* positive — STATUS.md §d24 auto_tune results — so these go live only if a confirming 2nd seed holds).
   - **Mobility-aware selection.** Today selection maximizes immediate gain (`-Δcov, Δcomp, Δdead`, free-before-costed); the alternative biases toward commits that keep the most *future* keeps viable (close off the fewest neighborhoods). Needs lookahead (train+eval the pool after each tentative commit): exact ≈100× a round, tractable only restricted (top-M × sampled pool). **No cheap predictor found** — committed Δcomp magnitude is uncorrelated with disruption (corr ≈ −0.09); `n_died`/Δdead correlate weakly (~+0.5) but too noisily to select on (same churn → 0 or 70+ closed). The right objective is distinct-*coverage* keeps kept open, not raw count. Open whether it even changes the *final* set or only the order/speed.
   - **Replacement / remove-and-reinsert local search.** At convergence, pop each keep back into the pool and rerun — a kept K may be *blocking* a better K' for its slot. The LOO/cleanup doesn't cover this (it removes dead weight; it never asks "this keep earns its slot, but would a *different* one earn more?"). Full pop-each+rerun ≈ N fixpoints (days, mostly re-committing K); a **bounded** version reuses computed data — test only *swaps* between the near-miss final LOGs and the low-margin keeps (smallest live-LOO contribution), accepting only strict lexicographic improvements (so it terminates).

## State layout
`audit/` is checked in (durable) and now holds the **canonical comptol6 run at the top level**: `checkpoint.json` (resume/rebuild state: kept set, reference metrics, per-candidate verdicts + the in-progress round) + `ledger.md` (human-readable; both rewritten every eval batch — `--eval-batch`, default 30 candidates) + `lineage.jsonl` (per-keep born/died + firing shifts). The rounds journal in `checkpoint.json` records `cleanup` (LOO ejections), `vetoed` (net-commit rejections), and `released` (cooldown stall releases) events — the cooldown bench is derived purely from this journal, and the journal replay (`kept` at any round; e.g. `--upto 194`) is what powers `--rerun`, the `--trajectory` frontier, and promotion of any prefix. To resume/rerun, point `--state-dir` at `audit/` itself. Per-candidate training is in-memory (the cached trainer), not written to disk.

**Keep-tokenizer retention**: each commit's tokenizer (~0.5 MB) is saved to `<work-base>/kept_tokenizers/<state-dir-name>/keep_<N>/` (N = kept-count) — consumed by `tools.token_lineage`. Caveat since ejections/transactions: N is reused and overwritten when the kept-count revisits a value, so these dirs hold only the latest tokenizer per cardinality, not a full per-round history — round-trajectory reconstruction goes through journal replay + retrain instead (`tools.generalization_check_cached --trajectory`, ~30s/point). Gitignored (binary, re-derivable), so a fresh machine re-trains.

**Fresh-shard instruments** (never used in train/gate/discovery roles; for honest post-hoc measurement only): `~/.cache/nanochat/base_data_climbmix_holdout2/` (shards 06522–31) and `holdout3/` (06512–21), consumed by `tools.generalization_check_cached`. The gate shards (06532–41) carry all selection pressure (they were a valid instrument for End-game item 1's check, which predates the fixpoint selecting on them); the val shard (06542) is the miner's discovery corpus + the `mangled_tune` diagnostic — neither is a valid generalization instrument now.
